# BLE 能力边界与普通 Beacon 规划

SDK 2026.10.28.1 / API 2.16 增加 `ble_open`，保留旧 BLE ABI。冻结、上线和实机证据分别记录；正式设备以已安装固件和所选发行版为准。

## 当前已经提供什么

| 需求 | 当前公开接口与边界 |
| --- | --- |
| 自定义服务的 GATT 外设 | `x622_ble_start` 的 mode=1，可声明应用 Service/RX/TX UUID 与名称 |
| 标准 HID 外设 | 同一入口的 mode=2，报告图、双输入报告及触摸 Feature 依最低 API 版本启用 |
| 记录型 GATT | `x622_ble_gatt_start`，mode=3；info/value、记录读取等见真实头文件 |
| 状态、停止与绑定隔离 | `x622_ble_status`、`x622_ble_stop`、停止后 `x622_ble_forget` |
| 连接后的发送 | `x622_ble_send` / `x622_ble_sequence`，不是广播数据提交接口 |
| 独立普通 Beacon | API2.16 `ble_beacon_*`，自有128位Service UUID、0..8 B服务数据，不可连接；任意广播载荷/制造商数据未开放 |
| 扫描与 Central | 当前没有公开接口，与外设或 Beacon 是不同能力 |

`BLE_ADVERTISE`（256）是历史权限名。底层固件为 GATT/HID 自动发布服务与名称，并不意味着 WASM 可以控制任意广播。WASM 不得自行导入 ESP-IDF/NimBLE 或传入宿主指针绕过限制。

可核对的来源：[主头文件](../sdk/xapp/x622_xapp.h)、[BLE 结构](../sdk/xapp/x622_ble.h)、[记录型 GATT](../sdk/xapp/x622_ble_gatt.h)、[机器可读 API](../api.json)。

## API 2.16 会话契约

配套API2.16固件的新 APP 使用 `x622_ble_open`，配置含 version=1、size=236、显式 STREAM/HID/RECORDS 角色。定义见[会话头文件](../sdk/xapp/x622_ble_session.h)，最小用法见[BLE 示例](../examples/ble-session/README.md)。HID 报告 ID 使用独立字段；不再借用 UUID 字节。所有角色共用原有单一后端，旧 start/记录型 start 保留原220 B配置与原有最低版本；状态36 B、帧24 B及队列容量不变。

本地 C 回调测试覆盖 GATT、记录、单/双报告及触摸 Feature、认证和绑定隔离、排队/重试/抬手、反复启停与失败清理；WAMR 测试覆盖真实控制桥、API/权限拒绝、未对齐配置、越界陷阱及冻结旧包启动回放。控制器/射频为桩，尚未进行真机验收。

主机 x86 桩中的单次会话分配从5280 B降为GATT3736 B/HID2464 B；后继HID队列的无效唤醒从2次降至1次，帧后30ms延时不变。这些不是 ESP32 总堆、功耗或帧率数据；目标连续空闲块、栈低水位、无线发送延迟和UI帧时间仍未测。没有放大缓存/MTU或改配对安全来换性能。

## 普通 Beacon 的设计与剩余实机验收

目标是让自有应用通过自己的服务 UUID 发布可由测试接收器读取的状态，例如设备发现、传感器状态与邻近识别。第一版采用结构化服务数据，由固件编码和管理身份；不以第三方系统弹窗、设备冒充或通知轰炸作为兼容目标。

| 工作项 | 建议与验收 |
| --- | --- |
| 会话与数据 | 为普通 Beacon 提供开始、更新、状态、停止操作；APP 只提交自定义服务 UUID 与有界数据，由固件声明支持的长度和编码；不要把连接发送接口复用为广播 |
| 参数与身份 | 固件校验配置并公布实际生效值、参数范围及不支持错误；身份与隐私由系统管理，不把内部对象、密钥或驱动句柄交给 APP |
| 调度与内存 | 复制参数，异步执行；有界队列、更新合并与明确背压；计算 BLE 与 UI/音频共存的峰值及最大连续分配，不在 APP tick 中睡眠等待 |
| 权限与兼容 | 明确普通 Beacon 权限、最低 API 与能力发现方式；新增版本化、固定大小结构，保持旧 GATT/HID ABI 和行为；默认不扩大无线并发 |
| 生命周期 | 复用系统无线租约；退出、trap、超时或启动失败均停止并确认释放；迟到回调不能恢复广播或访问已卸载 APP |
| 观察与验证 | 测参数错误、容量边界、更新背压、反复启停、退出与失败清理；受控接收器观察数据变化和停止后的空口状态，随后回归旧 GATT/HID 应用 |

开始调用成功只代表本机接受或完成对应阶段，不能证明接收端收到，更不能承诺某个手机系统产生特定界面。空口、接收端应用和 UI 流畅度要分别验证。

实现以所用ESP-IDF/NimBLE和目标芯片的真实支持为准：[Espressif ESP32-C3设备发现文档](https://docs.espressif.com/projects/esp-idf/en/stable/esp32c3/api-guides/ble/get-started/ble-device-discovery.html)。本地实现契约为 [x622_ble_beacon.h](../sdk/xapp/x622_ble_beacon.h)，权限仍为256。已记录一次独立 Windows BLE 扫描器收到自有UUID服务数据，以及同一历史CH343固件的10轮前台生命周期；后续固件尚须配对复验，退出后系统BLE恢复曾被内存准入拒绝，不能扩大为整机通过。

## 单一后端升级与旧包适配

采用用户要求的方式：直接优化现有蓝牙后端，旧 APP 在入口适配，新 APP 使用新版 SDK 推荐接口。不维护两套协议栈或两组常驻工作线程。当前固件本来就是单个按需创建的外设会话；升级应保留这个性质，不能把已有设计当作新增收益。

旧 APP 的导入名、签名、220 B 配置、24 B HID 帧、36 B 状态结构与错误语义继续有效。旧配置在启动入口校验后一次转换为内部描述，运行期间只保留需要的会话数据；每次旧操作做必要的命令映射，返回状态按旧布局编码。不要在每帧重新转换配置，也不要给新版 APP 嵌入旧 ABI 兼容库。

新入口使用显式版本、大小与角色，未知组合直接拒绝。不能只按大小猜测格式：现有 mode=1/2 配置与记录型 GATT 的 mode=3 配置均为 220 B，但分别从不同入口进入。旧请求继续经过原有权限和最低 API 校验，不因转换获得额外能力。

### 优先检查的性能点

下表是本地实现已处理的源码问题；收益以以上主机测量为限，目标硬件效果仍待验收：

| 源码现状 | 优化方向与约束 |
| --- | --- |
| 每个外设会话同时包含 GATT RX、TX 与 HID 序列存储 | 已按角色单次分配；HID 不保留闲置 GATT 环，GATT 不保留闲置 HID 队列；旧队列容量及背压语义不变 |
| RX 入队/出队有逐字节环形拷贝 | 已改至多两段连续拷贝；先校验长度与空间，复制全部成功才提交整条记录；容量不足不出队 |
| 记录型 GATT 值读取/更新会复制完整描述 | 已只复制有效字段；通过字节复制处理未对齐封套，不改变公开 ABI |
| 发送由原生事件队列和 callout 推进 | 保留事件驱动，删除两处有测试证明的无效唤醒；配对超时、失败重试和 HID 抬手保护不变 |
| WASM 边界与发送队列之间有安全复制 | 只消除多余中间副本；异步代码必须持有宿主拥有的数据，不能借用 WASM 指针、已返回的栈对象或卸载后的内存 |

不要用统一放大 MTU、缓存、任务栈或提高无线活跃度代替优化；这些可能增加 RAM、功耗或影响触摸报告时序。线程/锁和异步回调的生命周期先正确，再按测量结果调整。

### 兼容与负载验收

1. 固定当前固件与原始旧包作为基线，不重编旧 APP。用相同设备、场景、接收端和连接条件做前后对比。
2. 不启用 BLE 时不为兼容层启动任务或分配会话缓存；旧 BLE APP 的峰值 RAM 目标不高于基线，并比较最大连续空闲块、任务栈低水位及退出后的回收。
3. 分开记录启动耗时、调用延迟分位数、发送排队至通知提交延迟、队列满/重试次数、原生唤醒频率，以及 UI 帧时间。没有接收端证据不能把通知提交计为送达。
4. 回归 GATT、记录型 GATT、单/双报告 HID 与触摸 Feature：连接、配对、重连、订阅、顺序/延时、抬手、错误、退出与绑定隔离均不变。关闭安全验证或清除全部绑定不算优化。
5. 新旧入口在等价角色、数据和参数下表现一致；混合切换、旧队列饱和、异常退出、迟到回调及低内存失败均可恢复。分别给出主机与目标设备证据，未测项保留未测。

兼容转换会增加少量代码和执行工作，不能承诺零成本。目标是避免额外常驻资源，并让缓存与调度的收益覆盖适配成本。真正启用新无线功能时，其无线占用、CPU 和 RAM 仍须单独预算；尚未实现时不能给出负载百分比或宣称更快。

## 给主对话的可用任务文本

> 请直接升级现有单一蓝牙后端，保留旧导入、签名、结构、权限与行为；在入口把旧配置一次归一化，旧操作与状态做薄适配，新 APP 使用新版推荐 API，不维护双协议栈。新格式显式标注版本/大小/角色，不按 220 B 长度猜格式。优先测量并优化按模式缓存、环形拷贝、描述符复制与无效唤醒，保持宿主拥有异步数据及 HID 释放保护；不靠扩大缓存或改变连接策略制造提升。将原始旧包与当前固件作为基线，比较 RAM、连续块、调用/发送延迟、唤醒与 UI 帧时间，并回归 GATT/HID/记录型 GATT 的完整生命周期。在同一后端评估普通 Beacon，供自有 APP 用自定义服务 UUID 发布有界状态数据；不以第三方系统弹窗或通知轰炸为目标。按明确授权范围实施，未经授权不烧录；接口落地后同步头文件、宿主导入、验证器、api.json、SDK 快照、示例和 AI 能力规则，以实际证据发布一致版本。

## AI 工作流怎样发现能力

用户的一句话入口不变。`workflow.py prepare --capabilities ble --inline-context` 会自动提供 BLE 的真实导入、头文件与 IO-01/IO-06 规则，无需让 AI 再读取完整规则库。

当前返回的内容包含2.16会话及独立Beacon真实头文件与版本门禁。每次发行需同批完成：

1. 从真实头文件生成 `api.json`，同步导入签名、最低 API、权限与 ABI 检查；不能仅修改提示词宣称可用。
2. 若使用新头文件，将其加入 `tools/workflow_context.py` 的 BLE 能力映射及 SDK 发行文件清单，确保一次 prepare 能拿到完整结构和声明。
3. 更新 IO-01、API 手册及本文件状态，提供已实现能力的最小示例和失败/退出测试。现有独立 Beacon 契约已经本地实现；新示例必须覆盖开始／更新／停止与失败退出，不把单次旧固件空口证据外推到所有目标。
4. 通过正式发行流程发布一致的 GitHub/Gitee/服务器文件和校验索引；目标设备固件版本不足时明确报错，不能静默降级或换接口。

当前仅在本地同步设备代码、公共头文件、导入、验证器、api.json、示例及规则；权限位与包格式不变。当前不提交、打标签、冻结或部署；待维护方确认候选范围及最终设备验收通过后再执行同发行同步。AMBE仍为默认关闭且未验证语音能力，不能随2.16主能力一起描述成可通话。
