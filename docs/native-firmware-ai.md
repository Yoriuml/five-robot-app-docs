# X622 原生固件：AI 开发入口与硬件合同

文档版本：`native-hardware-2026.10.29.1`。适用设备：X622／五号机器人。

本入口用于生成独立 ESP-IDF 原生固件，交付完整工程和 `.bin`。它与安装在官方系统内的 `.xapp` 是两种开发目标；SDK 中的 `native-ui` 模板仍然是 XApp。本文提供硬件合同和执行规范，不代表已经提供或验收了一套完整的独立固件 BSP。

## AI 执行方式

1. 阅读本文件并结合用户需求直接开发。常规实现细节自行决定；真正缺失的外部凭据或相互矛盾的硬件信息才需要询问。
2. 本目标不使用 XAPP／WASM SDK，也不执行 `tools/workflow.py`。首次只下载本 Markdown，复用现有 ESP-IDF 环境和工具缓存；按需获取官方组件，不为阅读本文克隆整个仓库或下载完整 SDK。
3. 一个镜像读取失败后切换另一镜像，不反复重试相同地址。如果原文返回空或 HTML 错误页，不视为下载成功；GitHub 文件还可通过 `https://api.github.com/repos/Yoriuml/five-robot-app-docs/contents/docs/native-firmware-ai.md?ref=main` 获取 JSON，再解码 `content` 的 base64。
4. 在独立目录生成完整源码与资源，不覆盖官方系统源码。未经明确授权，不连接、烧录、擦除设备，不执行 eFuse 或安全锁定操作。
5. 优先完成可见首屏、输入与电源保持，再接入所需音频和网络。不要只交方案、截图或伪代码。

## 1. 主控与开发环境

- ESP32-C3，单核 RISC-V，160 MHz。
- 外置 P25Q128 Flash，128 Mbit／16 MB；按片内 RAM 预算，不假定存在 PSRAM。
- 使用 ESP-IDF 6.1、C/C++、FreeRTOS；编译目标为 `esp32c3`。
- 需要 GUI 时可用 LVGL 9.5，需要音频时可用 `esp_codec_dev` 1.5.6。固定所用依赖版本并保留锁文件；不需要的组件不要加入工程。
- 原生固件直接使用 ESP-IDF 和设备驱动，不导入 XApp 宿主 API。

## 2. 共有 GPIO 接线

| GPIO | 功能 | 说明 |
| --- | --- | --- |
| 0 | I²C SDA | PCA9557 与 ES8311 共用 |
| 1 | I²C SCL | 400 kHz |
| 2 | K1，左键／电源键 | 低有效、内部上拉 |
| 3 | 电池 ADC | ADC1 Channel 3，100 kΩ＋100 kΩ 分压 |
| 4 | LCD SPI SCLK | SPI2 |
| 5 | LCD SPI MOSI | 只写，无 MISO |
| 6 | I²S DOUT | 主控向 ES8311 输出声音 |
| 7 | I²S DIN | 主控接收 ES8311 麦克风数据 |
| 8 | I²S BCLK | 音频位时钟 |
| 9 | K4，上键／BOOT | 低有效、内部上拉 |
| 10 | I²S MCLK | 音频主时钟 |
| 11 | VDD_SPI | 保留不用，不输出 PWM，不擅自配置或烧写相关 eFuse |
| 12 | I²S WS | 音频声道时钟 |
| 13 | 功放使能 | 高有效，启动时先保持低电平 |

电池电压为校准后 ADC 引脚电压的 2 倍。必须处理 ADC 校准失败、读取失败和无效电压，不能只把原始计数当电池电压。

## 3. 两种硬件版本

两版共有接线相同，以下部分不同。用编译期板型配置隔离，并使用不同构建目录。用户未指定板型时分别生成两版构建目标和产物，不通过探测冲突引脚猜板型，也不把某个 COM 号当板型。

| 项目 | `ch343-v1` | `native-usb-v2` |
| --- | --- | --- |
| K2／中键 | GPIO19 | GPIO21 |
| K3／下键 | GPIO18 | GPIO20 |
| K1／左键、电源 | GPIO2 | GPIO2 |
| K4／上键、BOOT | GPIO9 | GPIO9 |
| USB 数据链路 | CH343P 转 UART0 | ESP32-C3 原生 USB Serial/JTAG |
| UART0 TX／RX | GPIO21／GPIO20 | 不在这两脚启用 UART0 |
| 原生 USB D+／D− | 不启用，GPIO19／18 是按键 | GPIO19／GPIO18 |
| PCA9557 输入掩码 | `0x0D`，IO0／IO2／IO3 输入 | `0x05`，IO0／IO2 输入 |
| 充电检测输入 | IO3，低有效 | IO0，软件约定低有效，实物极性需验证 |
| 背光输出 | IO7 | IO3＋IO7 |

- K2／K3 同样低有效、内部上拉。
- CH343P TXD 接主控 UART0 RX GPIO20；CH343P RXD 接主控 UART0 TX GPIO21。
- 旧板 GPIO18／19 已接按键，不启用应用阶段的原生 USB；新板不得把 USB 数据脚配置为按键。
- 新板 GPIO21 同时是 ROM UART TX 引脚。应用中的控制台选择不改变 ROM 行为；按住相应键上电的电气安全需要由实物电路确认。
- 软件连线合同不等于实物验收。若用户指出 PCB 标号或空间位置不同，先核对实物，不套用 XApp 历史 CONFIRM／BACK 事件名来猜位置。

## 4. PCA9557：电源、屏幕控制和状态输入

I²C **7 位地址 `0x19`**。寄存器：输入 `0x00`、输出 `0x01`、极性 `0x02`、方向 `0x03`；方向位为 1 表示输入，极性寄存器使用 `0x00`。

| PCA IO | 用途 | 电平／方向 |
| --- | --- | --- |
| IO0 | 旧板未连接；新板充电检测 | 两版都保持输入 |
| IO1 | IOEN 电源保持 | 输出，高＝保持开机 |
| IO2 | USB 5 V 存在检测 | 输入，高有效 |
| IO3 | 旧板充电检测；新板第二路背光 | 按板型选择方向 |
| IO4 | LCD DC | 输出，命令低、数据高 |
| IO5 | LCD CS | 输出，低有效 |
| IO6 | LCD RESET | 输出，低有效 |
| IO7 | 背光 | 输出，高有效 |

必须尽早初始化电源域。热重启时保护已经置高的 IO1，合法开机后保持 IO1 为高并读回确认；更新 LCD／背光时不可误清除 IO1。保留已有电源保持时，不能先写一个清零 IO1 的默认输出字节，再把它重新置高。

使用输出寄存器影子值和互斥锁更新位，不用输入寄存器推算输出值，不驱动输入脚。先安全释放需要作为输入的脚，再设置输出锁存和最终方向。

电池供电时释放 IO1 可以关机；USB 供电时释放 IO1 不代表能物理断电，应进入明确的关机待机状态。关机前停止业务、关闭功放和背光。充电检测与 USB 存在检测是两个信号，不能混用。

旧板 IO7 只支持数字背光开关，不能用 GPIO11 实现背光 PWM；新板 IO3＋IO7 为离散输出组合，不代表连续 PWM 调光。

## 5. ST7789 屏幕驱动

- 240×240，RGB565，SPI2，Mode 0，请求时钟 80 MHz；记录实际时钟。
- MOSI＝GPIO5，SCLK＝GPIO4；无 MISO，硬件 SPI CS 配置为未使用。
- **DC／CS／RESET 都通过 PCA9557，不是 MCU 直连 GPIO。**不能直接把 PCA IO 编号填进普通 `esp_lcd` SPI GPIO 配置。使用能正确控制扩展 IO 的传输层。
- 同一屏幕事务中，先通过 PCA 拉低 CS，正确切换 DC，发送窗口命令和像素；确认 SPI 传输结束后再释放 CS。不要在像素 DMA 尚未完成时改 DC／CS 或复用缓冲。
- 初始方向 `MADCTL=0x00`，像素格式 `COLMOD=0x05`，开启反色，地址范围从 0 开始。
- 参考初始化顺序：关闭背光 → RESET 低 10 ms → RESET 高后等待 120 ms → `0x01` 软件复位，等待 120 ms → `0x11` 退出休眠，等待 120 ms → `0x36,0x00` → `0x3A,0x05` → `0x21` → `0x29` → 绘制首屏 → 开启背光。
- 像素窗口使用 `0x2A`、`0x2B`、`0x2C`；每次重新开始像素写入仍需正确发送 RAMWR。RGB565 上屏处理好字节序，提供红绿蓝色块自检。
- 优先局部刷新、合并相邻脏矩形和内部 DMA 条带缓冲，例如 `240×40×2` 字节；避免无必要的全屏双缓冲以及每个像素一次 I²C 控制事务。
- LCD 控制与 ES8311 共用 I²C，统一锁顺序。不能在 ISR／SPI 回调里执行阻塞 I²C；不要持有控制锁等待音频队列或网络。

## 6. ES8311 音频

- Codec 是 ES8311，I²C **7 位地址 `0x18`**。若所用 `esp_codec_dev` 控制适配层要求左移地址，则传 `0x30`；按真实接口约定处理，不能在普通 7 位 I²C API 中传 `0x30`。
- 主控为 I²S 主机，标准 Philips 格式，16 bit、单声道，MCLK 通常为采样率的 256 倍；引脚见共有表。
- 24 kHz 可作为基础配置；其他采样率必须同时正确配置 Codec、MCLK 和 I²S，输入与输出数据格式也必须匹配。
- 按需初始化录音／播放。仅播放时不要额外申请录音 DMA；由一个明确的所有者负责通道启停，避免应用和 Codec 库重复 enable／disable。
- 功放先保持关闭，完成 Codec 复位、时钟、DMA 和输出稳定后再开启；停止时先关闭功放。延时必须实际让出 CPU，不能使用换算为 0 tick 的等待。
- 按键音与应用音频由统一音频管理器协调，不分别抢占、切换采样率或重建 I²S。
- 音频队列、录音缓存和网络缓存设定上限，处理欠载、背压、取消、失败及释放。需要持续收音时不能因 UI 动画而停供。

## 7. 产品交互、视觉和资源规则

- 中键执行主要动作，左键返回，上下键选择／调整。按下、松开、持续按住和组合键按需求正确处理；电源长按独立处理。
- 消抖和长按使用非阻塞状态机，不等待松手而堵塞主循环，不让联网重试阻塞输入或显示。
- UI 默认中文，直白、美观，突出主要内容，不堆小字说明；不强制添加无关教程和状态小标签。
- 不使用 Noto Sans SC。中文可选许可允许的 HarmonyOS Sans SC 或用户指定字体，随工程提供许可证并裁剪实际字形；数字也要清晰美观。
- 动画按单调时钟的真实经过时间推进，采用非线性缓动。不能按循环次数计时；卡顿后不补跑一长串旧帧。优先稳定帧率和按键响应，不将桌面预览帧率当 C3 实测。
- 图片、字体和查找表尽量留在 Flash；限制缓存、队列和任务栈。不在逐帧路径反复分配堆内存，不因 Flash 足够就假定 RAM 足够。
- Wi-Fi、BLE、音频按需启停；成功、失败、取消和退出都要释放资源。避免忙等、无界重试、无限增长队列和长时间持锁。
- 需要联网时校验证书和响应，凭据不写入公开仓库或日志。不能通过关闭验证来掩盖网络错误。

## 8. 构建、分区与交付

1. 先复用已有 ESP-IDF 和工具缓存，缺少 API 时核对对应版本的官方头文件，不编造声明。
2. 交付完整源码、CMake、依赖与锁文件、`sdkconfig.defaults`、明确的分区表、资源、许可证和可复制的构建命令。两种板型使用独立构建目录。
3. 这是独立固件工程，自定义分区必须与实际产物一致。若用户要求保留官方恢复系统或现有数据，必须先获取并核对目标设备的真实分区表和兼容合同，不猜偏移、不套用普通开发板布局。
4. 只有真实构建完成后才交付各板型 BIN、ELF、构建生成的地址清单及 SHA-256。需要合并镜像时按构建地址生成，明确完整镜像与单应用镜像的区别。
5. 不把独立固件宣传成能用官方 XApp 安装入口或现有官方 OTA 直接安装，不伪造官方签名和发布元数据。未经用户授权不烧录、擦除、迁移分区或修改 eFuse。
6. 检查可见首屏、按键、电源保持、关机，以及需求涉及的音频、网络和失败清理路径。报告静态资源、DMA 需求、堆峰值和任务栈；未实际测量的数值标明估算。
7. 分开记录编译、主机测试、预览和实机测试。工具缺失时交付可复现源码并明确未完成构建；没有实机证据，不宣称设备运行、音频或帧率通过。
