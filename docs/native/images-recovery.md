# 镜像、分区、烧录与恢复

专题 ID：`images-recovery`。交付 BIN、保留官方系统或处理下载故障时读取。以下命令／流程是操作说明，不代表 AI 已获准访问设备。

## 三种产物先分清

| 产物 | 用途 | 不可混用 |
| --- | --- | --- |
| `.xapp` | 官方系统的应用安装器 | 不是启动固件，不能按 Flash 地址直接烧 |
| ESP-IDF APP `.bin` | 某一应用分区的程序 | 不是从地址 0 写的完整镜像 |
| 合并完整 `.bin` | 同次构建的启动器、分区表和指定数据／应用 | 写入范围可能覆盖系统、设置、主题和 APP |

`.elf` 用于符号／调试，`.map` 分析链接占用；不要当烧录镜像。官方签名 OTA 有自己的封装、型号、版本和验签规则，不能把独立 APP BIN 改后缀当官方 OTA，也不能伪造官方签名。

## 独立新工程与保留官方系统是两条路径

独立工程可以采用与实际功能匹配的 16 MiB 分区表，完整交付该表和生成物；它不自动继承官方恢复系统、XApp 安装器、商店或 OTA。分区定义、链接大小、Flash 实物容量必须一致。

用户要求保留官方系统／应用／恢复入口时，**先确认目标设备当前布局、启动器、系统版本与备份**，再评估兼容性。不同历史布局都可能存在；不要凭“都是 16 MB”套同一偏移，不把普通 `idf.py flash` 当无损升级。即使只写主槽，也可能破坏官方行为或恢复兼容，需独立兼容验证。

供排查用的官方 `staged2` 源码布局快照如下；这是本资料核对版本的事实，**不是给任意设备执行的烧录表**：

```csv
# Name, Type, SubType, Offset, Size
nvs,      data, nvs,      0x9000,   0x6000
phy_init, data, phy,      0xf000,   0x1000
otadata,  data, ota,      0x10000,  0x2000
sysdata,  data, nvs,      0x12000,  0xe000
main,     app,  factory,  0x20000,  0x3c0000
recovery, app,  ota_0,    0x3e0000, 0x80000
appfs,    data, 0x40,     0x460000, 0xb80000
coredump, data, coredump, 0xfe0000, 0x20000
```

main＝3.75 MiB、recovery＝512 KiB、appfs＝11.5 MiB；合计至 16 MiB。`otadata`／恢复流程由官方 staged2 启动协议管理，不能按普通 IDF A/B OTA 的数据格式重置。主／恢复和两种板型均有身份约束，不重标错误型号，不拿另一版镜像兜底。

## 构建产物与地址

从**本次实际构建目录**读取 `flasher_args.json`／构建生成的地址文件、`project_description.json`、sdkconfig 和分区表 BIN。不要硬编码 ESP32 的 `0x1000` 启动器地址给 ESP32-C3，也不要猜 APP 必在 `0x10000`。IDF 分区表一般默认在 `0x8000`，但仍以本次构建配置为准，见 [IDF 分区说明](https://docs.espressif.com/projects/esp-idf/en/latest/esp32c3/api-guides/partition-tables.html)。

生成完整镜像可使用所装 IDF 的 `idf.py merge-bin`，先读该版本 `--help`，明确输出格式和起始偏移；它不能自动替用户准备未包含的文件系统／工厂资产。镜像内的空洞／填充也属于写入范围，不能因为某段都是 `0xFF` 就承诺不覆盖数据。

交付清单逐项包含：板型、芯片、Flash 容量、IDF 版本、工程／构建 ID、文件用途、大小、SHA-256、写入地址、预计覆盖范围、是否包含文件系统及所需引导配置。BIN 必须与同包 ELF／map／表来自同次构建。

## 获授权后的操作顺序

1. 枚举实际端口与板型，确认对应设备。COM10／13／18 都只是某台电脑的编号；不能固定。关闭自己持有的监控／串口连接，用户其他软件占用时提示，不擅自终止。
2. 在明确授权后读取芯片／Flash ID、实际布局和所需备份；备份记录地址、大小、SHA-256 并妥善保护，其中可能含凭据。不是 16 MiB 时按硬件异常处理，不改成另一容量掩盖。
3. 确认完整重刷还是特定区域更新，擦除是否被授权、哪些数据会丢失。单纯“编译一个固件”不授权擦除或烧录。
4. 按本次地址清单与正确板型烧录，校验写入结果，释放端口，再复位验证启动、电源、画面、输入和本次功能；失败保留完整日志与原镜像。

恢复官方系统需要用户实际对应硬件的可信完整包／恢复方案；本资料没有附带正式签名镜像或私钥。不承诺任意第三方原生固件可以从官方恢复入口自动退回。

## 自动下载与串口故障

CH343 板先用保守的 115200 握手，确认芯片／stub 后才提速；921600 是常用目标，5,000,000 不是所有芯片／线缆／驱动都稳定。记录实际使用的速率而非只显示请求值。重开串口可能导致板复位，不能无限停在 Connecting；阶段要有截止时间、清理和错误状态。

提速后出现数据流停止／噪声／校验错误时，先结束旧 reader／writer 并确认端口关闭，重新握手后使用较低速率有限重试；不要在未确定串口归属时多个 loader 同抢一台，也不要无休止重置正常设备。原生 USB 的 line coding 和 UART 物理波特率不同，不能用 CH343 控制线序列盲套新板。

自动下载失败时，按本板已确认的 BOOT／复位方式进入 ROM；K4＝GPIO9 是 BOOT，但不存在的 RESET 按钮不能写进说明。USB 重插、供电保持和复位路径要结合实物，不能通过试烧 eFuse“修好下载”。

批量烧录必须每台独立传输对象、状态和关闭流程，真正校验每台；并发数根据 USB 控制器、带宽、供电和主机负载验证，不能把“打开 10 个端口”等同于 10 台稳定通过。当前文档没有宣称某个并发数量已实测。
